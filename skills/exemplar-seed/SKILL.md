# Seeding a system with exemplar sample data

exemplar makes fake but consistent records: people, their companies,
addresses, phones, dates, amounts and prose, the same person everywhere they
appear. You describe the target system's shape in a record schema file,
generate records with `exemplar generate --local`, turn each into the
target's request bodies, and create them in the target, parents before
children.

## Rules

1. **Only fake data goes in.** Everything exemplar generates is fake by
   construction. Never mix in real customer data, and don't copy records out
   of the target to use as sample data. The only values you take from the
   target are its own lookup IDs (users, statuses, priorities), passed as
   lists.
2. **Ask before writing to a system.** Confirm the target and environment
   with the user before creating anything: a test, staging or demo instance,
   never production unless the user says so in those words. Say how many
   records of each kind you will create.
3. **Credentials stay in the environment.** Read the target's API token
   from an environment variable the user names. Never put one on a command
   line, ask for one in chat, print one or write one to a file.
4. **Start with one.** Generate and seed a single account first, check it in
   the target (API read-back, or the UI), then do the rest.
5. **Keep a record of what you created.** Write every created ID, with the
   generated record it came from, to a file outside the repository, so the
   user can check or remove it. Stop at the first failure and report it;
   don't retry blindly or skip records silently.
6. **Keep it reproducible.** Note the seed, the schema file and the lists
   file. The same three give the same records.

## 1. Write the schema

Read the target's API description (an OpenAPI file, or its docs) for the
create endpoints, not the read models: what a `POST` accepts is what you
generate. Pick the fields a realistic record fills, not all of them; most
APIs need few. Write one schema per tree, usually one record per customer
holding its contacts, deals and their children, so seeding needs no IDs
across records.

```toml
name = "acme-account"          # lower-case letters, digits, '-'
exemplar = "0.5"               # the oldest exemplar the file needs
step = "company"               # one record per company
title = "{companyName}"
request_lists = ["users", "statuses"]   # the target's own IDs, given at generate time

[[fields]]
name = "companyName"           # the target's key, in its own case
value = "company.name"

[[fields]]
name = "owner"
pick = "@users"                # [{ "id": 101, "name": "…" }, …] from --lists
hidden = true                  # picked once, not output

[[fields]]
name = "idUserOwner"
value = "owner.id"

[[fields]]
name = "contacts"
list = { each = "company.contacts" }   # one item per person at the company

  [[fields.fields]]
  name = "email"
  value = "person.email"

[[fields]]
name = "deals"
list = { count = [1, 3] }

  [[fields.fields]]
  name = "status"
  pick = "@statuses"
  hidden = true

  [[fields.fields]]
  name = "idStatus"
  value = "status.id"

  [[fields.fields]]
  name = "value"
  money = [1000, 50000]
  format = "number"            # display "$1,234.56", number 1234.56, string "1234.56"
```

Each `[[fields]]` block is one key of the record: `name` is the key, and
one type key is the source of its data. Field types: `value` (copies the
person, company, `record.number`, `item.number`, a field above or a key in
one), `template`, `ref`, `pick`, `int`, `money`,
`date`, `text`, `bool = 0.8`, `const`, `object = true`, `list`, `sum`,
`percent`, `lines`; any field takes `optional = 0.2` (null that often) and
`hidden = true`. `exemplar schemas list --json` shows the built-in schemas;
`docs/generation.md` in the exemplar repository has every type, and
`docs/examples/crm-account.toml` a full example.

Check the schema with one record: errors name the field and what is wrong.

```bash
exemplar generate --local --kind records --count 1 --schema-file acme-account.toml --lists lists.json
```

## 2. Get the target's lists

For each name in `request_lists`, read the target's own values (its users,
statuses, priorities) through its API and write them to a JSON file of lists
by name. Keep only the IDs and names you need:

```json
{"users": [{"id": 101, "name": "Sales One"}], "statuses": [{"id": 1, "name": "Lead"}]}
```

## 3. Generate

```bash
exemplar generate --local --kind records --count 10 --people 30 --seed 42 \
  --schema-file acme-account.toml --lists lists.json > /tmp/seed/records.json
```

- `--count` is records (accounts, with `step = "company"`); `--people` is how many fake people they share, a few to a company. More people than records gives every account its own company.
- stdout is `{"seed": N, "records": [...]}`; stderr has the seed.
- `--local` needs no server or key. Without it, `exemplar generate <dataset> --kind records --schema-file … --lists …` stores the records as fixtures on an exemplar server instead (`EXEMPLAR_SERVER`, `EXEMPLAR_API_KEY`).

## 4. Transform and seed

Split each record into the target's request bodies with `jq` or a short
script, and create them top-down, putting each parent's new ID into its
children:

```bash
#!/usr/bin/env bash
set -euo pipefail   # stop at the first failed request
post() {            # post PATH BODY: create one, print the new ID
  curl -sf -H "Authorization: Bearer $TARGET_TOKEN" -H 'Content-Type: application/json' \
       -d "$2" "$TARGET_URL$1" | jq -er '.id'
}
while read -r acc; do
  id=$(post /customers "$(jq -c 'del(.schema, .contacts, .deals)' <<<"$acc")")
  echo "customer $id" >> /tmp/seed/created.log
  while read -r c; do
    cid=$(post /customerContacts "$(jq -c --argjson id "$id" '. + {idCustomer: $id}' <<<"$c")")
    echo "contact $cid of customer $id" >> /tmp/seed/created.log
  done < <(jq -c '.contacts[]' <<<"$acc")
done < <(jq -c '.records[]' /tmp/seed/records.json)
```

Adapt it to the target: its auth header, paths, the key a child uses for its
parent, and any field the API names differently on write. Watch for rate
limits. When there is no API, seed through the UI with the browser, one
record at a time, from the same JSON.

## 5. Report

Tell the user what was created (counts per kind, the ID log's path), the
seed, schema and lists files, and anything that failed or was skipped. Don't
delete what you created unless the user asks.

## What not to do

- Don't hand-write sample values or ask a model to invent them: exemplar
  keeps people, companies and their details consistent, and the seed makes
  the run repeatable.
- Don't widen a schema to every field the API lists; fill what a real
  record would.
- Don't put a target's credentials or real customer data in a schema or
  lists file.

More: `docs/generation.md` ("Records for another system") and `docs/cli.md`
in the exemplar repository.
